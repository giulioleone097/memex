# Memex PRD — Self-Sufficient Agentic Wiki with Internalized Code+Knowledge Graph

- **Status:** Approved design, pending user review of this document
- **Date:** 2026-07-14
- **Supersedes:** extends `2026-07-11-openwiki-dual-plugin-design.md` (which remains the record for the existing runtime)
- **Decision owner:** Giulio Leone

## 1. Summary

Rename the `openwiki` plugin to **Memex** and evolve it into a fully self-sufficient agentic wiki: a dual-host (Codex + Claude Code) plugin whose deterministic runtime internalizes the capabilities the workflow currently borrows from external tools — GitNexus (code graph: query, context, impact, trace) and Graphify (concept graph: LLM-extracted concepts, communities, god nodes, agent-navigable wiki) — plus real semantic search via vendored embeddings. The product merges Karpathy's LLM-wiki pattern with GraphRAG: the agent compiles knowledge at write time; any agent gets instant (<1s), deterministic, cited answers at read time, offline, with no external runtime.

Operating principle: **compile at write, answer at read.** The agent pays the semantic cost once when it writes (init/ingest/update/enrich). Every later read — from any agent, any session, any host — is deterministic retrieval over the persisted graph and indexes, with zero LLM calls.

## 2. Background and current state (evidence)

The repository already contains a working `openwiki` 0.1.0 dual-host plugin (`plugins/openwiki/`, 21 TS modules, 5,697 lines, Node >= 20, zero runtime npm dependencies):

- **Runtime:** CLI (`dist/cli.js`), MCP stdio adapter, Git hook adapter, doctor, schedules, atomic confined storage under `~/.openwiki/`, redaction, typed errors with stable machine codes.
- **Native code graph (exists):** scanner + content-addressed shard store v2 with write lock (`graph-store.ts`), node kinds `repository|directory|file|module|symbol`, edge kinds `contains|declares|imports|exports|calls|inherits|implements|references`, confidence `exact|resolved|heuristic`, actions `build|status|query|context|impact|changes|map`. Read-only toward sources; stores metadata and hashes, never source bodies.
- **Wiki:** code mode + personal mode, standard pages (`quickstart.md`, `architecture.md`, `source-map.md`, `workflows.md`, domain/operations/integrations/testing), seven source kinds, provenance and Git evidence, `check`/`finalize` lifecycle.
- **Skills:** router, init, ingest, query, update, ops, graph.
- **Tests:** unit + integration + e2e suites; verification report at `artifacts/verification/final-report.md`.

Gaps versus the product vision: no semantic search (retrieval is lexical), no concept plane (docs/markdown knowledge is not in the graph), no wiki↔graph anchoring (pages are not graph nodes), no communities/god-nodes/path queries, and the plugin has never been exercised end-to-end on a real repository by its actual users.

### Reference tools studied

- **Graphify** (github.com/Graphify-Labs/graphify): pipeline `detect → extract → build → cluster → analyze → report → export`; LLM extraction at build time, no embeddings; edges tagged `EXTRACTED|INFERRED|AMBIGUOUS`; Leiden communities; god nodes; `query/path/explain`; SHA256 incremental cache; wiki export (`index.md` + article per community) for agent navigation; MCP server; measured ~71x token reduction per query on a 52-file mixed corpus.
- **GitNexus:** code knowledge graph with impact analysis, tracing, change detection; embeddings optional and off by default; external MCP dependency we internalize (read-side parity only).

## 3. Decisions made during brainstorming

| # | Decision | Choice |
|---|----------|--------|
| D1 | New name | **Memex** (Vannevar Bush's memory extender). Plugin/CLI/storage name `memex`. npm collision irrelevant (no npm publication; `memex-wiki`, `agent-memex` free as fallback). GitHub namespace is the owner's own; WorldBrain/Memex is an unrelated browser extension. |

| D3 | Testing meaning | **Real dogfooding** on real repositories with objective evidence, before refactoring. |
| D4 | Semantic search | **Real embeddings, self-sufficiently:** vendored WASM inference + quantized multilingual model, plus lexical BM25 and graph proximity, fused. Not API-based, not native-binary-based. |
| D5 | GitNexus parity | **Read-side parity only** (query/context/impact/trace/map/changes/communities). Source-mutating refactoring (rename) stays out of scope; the graph's read-only mutation boundary is preserved. |
| D6 | Architecture | Approach A: one unified graph, deterministic runtime answers reads, agent compiles semantics at writes. |

## 4. Goals

1. **G1 — Prove the current product** on real repositories (dogfooding) and convert every defect found into a fix with a regression test.
2. **G2 — Rename** the plugin, CLI, skills, storage, and documentation from `openwiki` to `memex`, with idempotent data migration `~/.openwiki/` → `~/.memex/`.
3. **G3 — Internalize the knowledge layer:** one unified graph holding code, concepts, and wiki pages; hybrid instant retrieval (BM25 + vectors + graph); communities, god nodes, path/explain queries; graph report; all exposed via CLI and MCP with bounded JSON contracts.
4. **G4 — Stay self-sufficient:** after plugin installation, no network, no credentials, no native compilation, no external tool is required for any operation.
5. **G5 — Remain agentic-first:** every capability is designed for agent consumption (bounded JSON, stable error codes, citations, confidence labels) and the wiki is maintained by the agent through the skills, never by hand.

## 5. Non-goals

- Source-code mutation tooling (symbol rename, codemods) — remains the host agent's job with its own tools.
- PDF/image/vision extraction — phase 3+, after v1 ships.
- Multi-user/server deployment, web UI, HTML graph viewer — the consumers are agents; `map`/`report` output serves the human.
- npm publication and public marketplace listing — repository stays private.
- Replacing host reasoning: the runtime never calls an LLM.

## 6. The self-sufficiency constraint, restated

The founding constraint evolves from "zero dependencies" to **"zero external runtime"**:

- **Allowed:** assets vendored inside the plugin at build time — the onnxruntime-web WASM engine (~5 MB, Apache-2.0), one quantized ONNX embedding model (~35 MB, int8), its `tokenizer.json`, all with recorded checksums and licenses (`plugins/memex/vendor/MANIFEST.json` + license files).
- **Forbidden at runtime:** network access, model-provider credentials, native compilation (node-gyp), `npm install`, spawning anything outside Node >= 20 and Git.
- **Consequence:** plugin size grows from a few MB to ~40–45 MB. Accepted (D4): completeness beats size for this product.

Embedding model: **`intfloat/multilingual-e5-small`, int8-quantized ONNX** (MIT license) — chosen because the wikis are Italian + English and e5-small keeps query latency in the 50–200 ms range on WASM. The model is a data asset described by a manifest (id, dimensions=384, revision, checksum, required `query:`/`passage:` prefixes); swapping models is a data change plus reindex, not a code change. Tokenizer: pure-TS implementation of the model's tokenizer, driven by the vendored `tokenizer.json`.

## 7. Delivery phases

Each phase is a complete vertical slice with objective evidence, and lands in order.

### Phase 0 — Dogfooding campaign (test what exists)

**Protocol.** Install the plugin for real in both hosts (Claude Code marketplace add + Codex plugin path). Run the full lifecycle on two repositories: (a) this repository itself — the wiki that documents itself — and (b) one production-scale repository selected by the owner at execution time. Exercise: `init` → wiki page synthesis → `graph build/status/query/context/impact/changes/map` → `ingest` (at least one real source) → `update` after a real commit → `check`/`finalize` → `doctor` → MCP session from each host → hook firing on commit.

**Evidence.** A dogfooding report at `artifacts/dogfooding/<date>-<repo>.md` per repository: commands run, JSON outputs, timings, wiki pages produced, defects found. Every defect becomes a tracked fix with a failing-first regression test.

**Exit criteria.** Both hosts complete the full lifecycle on both repositories with zero unexplained errors; defect list closed or explicitly deferred with justification.

### Phase 1 — Rename `openwiki` → `memex`

**Surfaces renamed:** repository directory `plugins/openwiki` → `plugins/memex`; plugin manifests (`.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`, both marketplaces); skill names `openwiki*` → `memex*` and every SKILL.md body; CLI identity and help text; MCP server name and tool titles; error message prefixes; env/hook identifiers; storage root `~/.openwiki/` → `~/.memex/`; docs and README. Version bumps to 0.2.0.

**Data migration.** A `migrate` operation (surfaced through `doctor`/ops): if `~/.openwiki/` exists and `~/.memex/` does not, move it atomically (same filesystem rename; fallback copy+verify+remove), write a migration record, and leave a tombstone file `~/.openwiki/MIGRATED.md` pointing to the new root. Idempotent; re-runs are no-ops. `status`/`doctor` on any operation detect an unmigrated legacy root and instruct the agent to run migration — no silent dual-root reads.

**Compatibility.** No dual-name support period: the rename is atomic within the repo, and old installs are handled by the migration path. State schema keeps its own version field; the rename does not change schemas.

**Exit criteria.** Full test suite green after rename; a fresh install and a migrated install both pass the Phase 0 lifecycle smoke run; zero occurrences of the string `openwiki` outside historical docs/changelog and migration code.

### Phase 2 — Intelligence layer

Delivered as three sequenced slices, each independently verified.

**2a — Unified graph: concept and wiki planes.** Extend graph contracts (v2 schema):

- New node kinds: `concept` (agent-extracted concept/entity/decision), `page` (a wiki page), `source` (an ingested source envelope).
- New edge kinds: `mentions` (page/concept → symbol/file), `describes` (page → concept/code node), `grounds` (source → concept/page: provenance), `related` (concept ↔ concept), `member-of` (node → community).
- Confidence model: deterministic scanner edges keep `exact|resolved|heuristic`; agent-authored edges carry `extracted|inferred|ambiguous` (Graphify semantics: stated in source / reasonable deduction / uncertain, surfaced for review). The two label sets are disjoint by plane and validated per edge kind.
- New `graph enrich` operation: the agent submits a validated batch of concept nodes/edges (same envelope discipline as `ingest`: size caps, schema validation, redaction, atomic write into the shard store). Enrichment shards are keyed by source-content hash, so re-enrichment of unchanged files is a no-op and stale enrichments are detected via the existing freshness machinery.
- Wiki lifecycle integration: `init`/`update`/`ingest` skills gain a mandatory enrichment step — after writing pages, the agent extracts concepts and mentions and calls `enrich`; `check` gains validations: every wiki page is a `page` node, every page has ≥1 `describes`/`mentions` edge with provenance, no dangling node references.

**2b — Embeddings and hybrid retrieval.**

- **Vector store:** new module storing embeddings in binary segment files next to graph shards (per-segment header: model id, dims, dtype int8/f32, count; entries keyed by node/chunk id + content hash). Chunking: wiki pages and markdown split at heading/paragraph boundaries (target 200–400 tokens), code symbols embedded from their signature + name + enclosing path (metadata text, not source bodies — preserving the "no source bodies in the store" guarantee; chunk text for snippets is re-read from the wiki/repo at answer time).
- **Inference:** vendored onnxruntime-web WASM engine + vendored model, loaded lazily on first embed; embeddings computed at write time (init/ingest/update/enrich) for all new/changed chunks; only the query is embedded at read time.
- **Lexical index:** BM25 postings + trigram index over the same chunk universe, stored as segments, rebuilt incrementally by content hash.
- **Hybrid retrieval:** new read operations `search` (ranked chunks/nodes) and `ask` (one-shot: retrieve → expand via graph → return bounded evidence bundle with citations). Ranking: Reciprocal Rank Fusion of BM25, cosine-over-vectors, and graph proximity (distance from lexical/vector seed nodes weighted by edge confidence). Every result carries: score, per-signal ranks, node/page/file citation with line ranges, confidence labels. Deterministic given the same store: ties broken by stable id order.
- **Performance targets (accepted):** `search`/`ask` p95 < 1 s end-to-end on a 5k-chunk workspace including query embedding; incremental reindex of one changed page < 2 s; full build of this repository < 60 s. Targets are asserted in e2e tests with generous CI margins (2x).

**2c — Structure analytics and the self-maintaining report.**

- **Communities:** deterministic label-propagation clustering (seeded by stable node-id order for reproducibility) over the unified graph; `member-of` edges persisted; `communities` read action lists communities with member counts and top terms.
- **God nodes and surprising connections:** degree/betweenness-lite analytics; cross-plane edges (concept↔code) rank above same-plane ones, following Graphify's insight.
- **`path` and `explain` actions:** shortest confidence-weighted path between two nodes; `explain <node>` returns the node, its neighborhood, communities, and citing pages.
- **Graph report:** `report` action renders `graph-report.md` as a wiki page (god nodes, communities, surprising connections, suggested questions, coverage stats, ambiguous edges pending review) — regenerated by `update`, so the wiki continuously documents its own knowledge state.
- **MCP surface:** all new read actions exposed through the existing MCP adapter with identical JSON contracts; `enrich` exposed as the single new write tool with the same authorization discipline as `write`/`ingest`.

**Exit criteria for Phase 2.** All new operations pass unit + integration + real e2e tests in both hosts; the Phase 0 dogfooding protocol re-run on this repository exercises `enrich`, `search`, `ask`, `path`, `explain`, `communities`, `report` with recorded evidence; token-efficiency measurement (answer-bundle tokens vs. raw-file tokens for 10 representative questions) is recorded in the dogfooding report.

## 8. Architecture

Three layers, one rule: semantics at write time is the agent's job; determinism at read time is the runtime's job.

```
┌──────────────────────────────────────────────────────────────┐
│ SKILLS (agent)                                                │
│  memex (router) · init · ingest · update · query · ops        │
│  · graph — now including the enrich workflow                  │
│  Compile: extract concepts, write pages, anchor provenance    │
├──────────────────────────────────────────────────────────────┤
│ RUNTIME (deterministic TS, zero external runtime)             │
│  contracts · storage/atomic · wiki · sources · state          │
│  graph: contracts/scan/store/index/query  (+ concept plane)   │
│  NEW  embed: tokenizer · ort-wasm loader · vector-store       │
│  NEW  retrieve: lexical(BM25+trigram) · hybrid-rank · ask     │
│  NEW  analyze: communities · centrality · report              │
│  errors · redact · doctor · schedules · git                   │
├──────────────────────────────────────────────────────────────┤
│ ADAPTERS (hosts)                                              │
│  CLI (dist/cli.js) · MCP stdio · Git hook · installer         │
├──────────────────────────────────────────────────────────────┤
│ VENDORED ASSETS (build-time, checksummed, licensed)           │
│  ort-wasm engine · multilingual-e5-small int8 · tokenizer.json│
└──────────────────────────────────────────────────────────────┘
```

New/changed modules (indicative): `graph-contracts.ts` (v2 kinds/labels), `graph-store.ts` (enrichment shards), `enrich.ts`, `chunk.ts`, `tokenizer.ts`, `embedder.ts`, `vector-store.ts`, `lexical-index.ts`, `retrieve.ts`, `analyze.ts`, `report.ts`; extended: `cli.ts`, `mcp.ts`, `contracts.ts`, `doctor.ts` (asset checks: model present, checksum valid), `paths.ts` (memex roots), plus the skills.

## 9. Data model and storage layout

```
~/.memex/
├── wiki/                        # personal-mode wiki (unchanged semantics)
└── data/
    ├── personal/                # personal-mode private data
    └── <workspace-id>/
        ├── graph/               # shard store v2 (existing) + enrichment shards
        │   ├── manifest.json    # shards, schema+scanner versions, Git fingerprint
        │   └── <hash>.json      # content-addressed shards (scan + enrich)
        ├── vectors/
        │   ├── manifest.json    # model id/rev/dims/dtype, segment list, checksums
        │   └── <hash>.bin       # embedding segments keyed by content hash
        ├── lexical/
        │   ├── manifest.json
        │   └── <hash>.json      # BM25 postings + trigram segments
        └── analysis/
            └── communities.json # persisted clustering + centrality snapshot
```

All stores follow the existing discipline: atomic writes, single write lock per store, content-addressed segments enabling incremental reuse, confined paths (no symlink escape), 0o700 modes, and manifests carrying schema/scanner/model versions so incompatibility is detected, never guessed. The graph never stores source-file bodies; vector/lexical stores hold only derived numbers/tokens plus `path#Lstart-Lend` references.

## 10. Data flow

**Write path (agent-driven):** host agent runs a skill → `context`/`changes` identify changed evidence → agent writes/updates wiki pages (`write`) → agent extracts concepts+mentions from changed pages/docs (`enrich`) → runtime validates, redacts, caps, and atomically persists shards → runtime re-chunks changed content, updates lexical segments, computes embeddings for new/changed chunks (WASM, local) → `check` validates cross-plane invariants → `finalize` seals the run with content hash + run id.

**Read path (instant, zero LLM):** any agent calls `search`/`ask`/`query`/`path`/`explain`/`impact`/... via CLI or MCP → runtime embeds the query text (only LLM-free model inference, ~50–200 ms) → BM25 + cosine + graph-proximity ranks fused (RRF) → graph expansion around seeds bounded by `--limit`/depth → bounded JSON evidence bundle with citations, confidence labels, per-signal ranks, and truncation metadata.

**Freshness:** the existing Git-fingerprint machinery plus content hashes drive incrementality everywhere; the post-commit hook notifies staleness; `update` reconciles wiki + graph + indexes in one run; a stale index is reported as stale, never silently served as fresh (staleness noted in every read response).

## 11. Error handling and safety

- Existing stable machine codes are kept; new ones added: `MODEL_ASSET_MISSING`, `MODEL_ASSET_CORRUPT` (checksum mismatch), `EMBEDDING_FAILURE`, `INDEX_INCOMPATIBLE` (model/schema version mismatch → instructs reindex), `MIGRATION_CONFLICT` (both roots exist with diverged content).
- Degradation is explicit, never silent, and scoped by operation (decision of record, 2026-07-16):
  - **Write paths** (`init`/`ingest`/`update`/graph build / `writePage` / enrich reindex) **soft-degrade** when vendor embedding assets are absent or checksum-invalid: the graph, lexical index, and wiki build normally, vector embedding is skipped, and the skip is recorded non-silently — `embeddingsAvailable=false` (with a machine-readable reason) in the vector-store manifest, surfaced by `doctor` and `status`. Writes never throw `MODEL_ASSET_MISSING`/`MODEL_ASSET_CORRUPT`. This keeps the plugin fully functional (graph + lexical + wiki + all existing workflows) in any environment without the ~142 MB assets, including the test suite. `EMBEDDING_FAILURE` and `INDEX_INCOMPATIBLE` (genuine faults, not "assets absent") still hard-fail.
  - **Read paths** (`search`/`ask`) hard-fail with the typed error only when a vector signal is required and unavailable; the agent may explicitly retry with `--signals lexical,graph`, and the response then labels itself `degraded`. No automatic silent fallback. This scoping matches the no-silent-fallback principle, which is a *retrieval* guarantee.
- The graph mutation boundary is preserved verbatim: build/enrich/index read repository files but never execute repository code and never write outside the private store; read actions stay read-only; refactoring stays out (D5).
- All external input (enrich envelopes, queries, paths) passes the existing validation/redaction/caps pipeline; UTF-8 validation and input framing limits (recent fixes) apply to the new operations too.
- Concurrency: vector/lexical stores adopt the graph store's write-lock pattern; readers never block writers (segments are immutable once written; manifests swap atomically).

## 12. Testing and verification

- **Unit:** tokenizer golden vectors (fixed strings → fixed token ids), chunker boundaries, BM25 math, RRF fusion, label propagation determinism, contract validation for new kinds/labels, migration idempotency.
- **Integration:** enrich round-trip (envelope → shards → query), vector store segment reuse on unchanged content, incompatibility detection (model-id change → `INDEX_INCOMPATIBLE`), CLI + MCP contract parity for every new action, hook-driven staleness.
- **E2E (real, non-mocked):** on the bundled fixture repo and on this repository — full lifecycle including enrich/search/ask/path/explain/communities/report from both host CLIs and both MCP sessions; embedding determinism asserted (same store + same query → same result ids); performance targets asserted with CI margin.
- **Dogfooding (Phase 0 and re-run in Phase 2)** with reports under `artifacts/dogfooding/`; defects become failing-first regression tests.
- **Gates per slice:** build, lint, typecheck, full test suite, broad non-regression of existing operations, two consecutive clean review cycles, evidence in the report. No slice is "done" otherwise.

## 13. Risks and mitigations

| Risk | Mitigation |
|------|------------|
| WASM inference slower than targets on older hardware | int8 model, lazy engine load, embed-at-write amortization; targets asserted with margin; model swappable via manifest. |
| Concept-plane quality depends on agent discipline | enrichment is schema-validated, capped, confidence-labeled; `check` enforces cross-plane invariants; `report` surfaces `ambiguous` edges for review; dogfooding measures real answer quality. |
| Repo size +40 MB (vendored assets) | accepted (D4); assets content-addressed and fetched once at build time into `vendor/` with checksum verification recorded in the repo. |
| Rename breaks live installs | migration operation + tombstone + doctor detection; smoke run on a migrated install is an explicit Phase 1 exit criterion. |
| Label propagation weaker than Leiden | acceptable for v1 (deterministic, zero-dep); clustering sits behind the analysis interface so the algorithm can be upgraded without contract changes. |
| Multilingual retrieval quality (IT+EN) | multilingual-e5-small chosen specifically for this; e5 `query:`/`passage:` prefix discipline enforced in the embedder; dogfooding includes Italian-language questions. |

## 14. Acceptance criteria (Definition of Done)

1. Phase 0 report exists for both repositories and both hosts; every defect fixed-with-test or explicitly deferred by the owner.
2. `memex` is the only product name in manifests, skills, CLI, MCP, storage, and docs; migration verified on a real legacy root; suite green.
3. On this repository, from a cold agent session: `memex ask "<question about the codebase>"` returns a cited, correct, bounded evidence bundle in under one second (excluding first-run model load), offline, in both hosts.
4. The wiki regenerated by `update` includes the graph report page, and `check` enforces page↔graph anchoring invariants.
5. All gates in §12 pass; dead code from the rename and superseded paths removed; final verification report updated under `artifacts/verification/`.

## 16. Amendments — 2026-07-14 (TV.1 acquisition evidence)

Corrections established during vendored-asset acquisition, superseding the estimates in §6 and the risk table:

1. **Real asset size.** int8-quantized `multilingual-e5-small` measures ~118 MB (the 250k-token XLM-R multilingual vocabulary dominates and is a structural floor for multilingual models; verified across 7 independent ONNX sources) plus ~17 MB `tokenizer.json`. Total vendored assets: **142 MiB** (149,020,859 bytes, 28 manifested files), not ~40 MB. Accepted: multilingual coverage (Italian+English) is a hard requirement and an English-only model is rejected; the vendor test enforces a real 160 MB ceiling.
2. **Chunked model storage.** `model.onnx` exceeds GitHub's 100 MB per-file push limit. Git LFS is rejected (external tool for every cloner). The model is stored as sequential raw parts < 95 MB each; `MANIFEST.json` records per-part sha256 plus the assembled sha256; loaders concatenate parts in memory (Uint8Array → `InferenceSession.create`), never reassembling on disk. The vendor test asserts no manifested file ≥ 100 MB.
3. **License correction.** onnxruntime-web is MIT, not Apache-2.0 (verified against the canonical LICENSE). The vendored license texts are authoritative.
4. **Runtime resolution note.** The ort Node entry requires the dependency-free `onnxruntime-common` package, vendored under `vendor/ort/node_modules/` (scoped .gitignore negation) so Node bare-import resolution works without any install step; the vendor test asserts nothing else can appear under that path.
