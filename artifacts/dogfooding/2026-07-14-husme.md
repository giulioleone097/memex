# Dogfooding report — Husme (T0.2, second repository)

Target: `/Users/giulioleone/Documents/Husme`. Plugin under test: `plugins/openwiki` (built `dist/`, no rebuild needed — `dist/` already present at session start). Node.js v25.9.0. All commands run against the target with `node plugins/openwiki/dist/cli.js <operation> --mode code --root <root> --json` unless noted. Per orchestrator instructions, host installer steps (Step 2 of the T0.1 brief) were skipped; the CLI and MCP server were exercised directly. No source code or business logic from Husme is quoted below — only paths, counts, dependency names, and structural facts.

## Target shape (read before interpreting any other section)

`Husme` is **not** a single repository. `git -C Husme status` shows it is itself a Git repository with **zero commits** (`fatal: your current branch 'main' does not have any commits yet`), containing two untracked top-level directories:

- `hausme-tech-interview-main/` — a plain directory (no `.git` of its own), ~4,437 raw filesystem entries, dominated by a `.venv` (Python virtual environment, ~12MB) and `.pytest_cache`. Both are excluded by its own nested `.gitignore`. Real, non-ignored source is 33 files / 67,604 bytes under `parte-1/` (two interview-exercise tracks: `esercizio-a-fix-no-ai`, `esercizio-b-fix-con-ai`, each with a `backend-l2` and `backend-l3` tier; one track adds a `frontend-nextjs` component).
- `hausme-tech-interview-pr/` — an **embedded Git repository** (has its own `.git`, one commit, branch `giulio/backend-l2-non-regression`, HEAD `3d78ab8d8e1704329e434b5c20d3593c2d5926b6`, dated 2026-06-10), clean working tree, same `parte-1` layout, 27 git-tracked non-ignored files.

This shape — an unborn-HEAD root containing one plain oversized directory and one embedded git repo — is a genuine, if unusual, real-world edge case (a workspace folder someone dropped two related checkouts into without ever committing at the top level), and it exercised several code paths T0.1 (this plugin's own repo) never touched.

**Scale-premise correction (concern, not a defect):** the assignment described Husme as "~3,600 source files" for PRD-scale timing. That estimate reflects a raw filesystem count. Once the plugin's actual Git-aware, `.gitignore`-respecting enumeration is applied (which is the correct, intended behavior — see `graph-store.ts` `enumerateRepositoryMetadata`, built on `git ls-files --cached --others --exclude-standard`), the real reachable corpus is **31 files** at the top-level root, **31 files** if rooted directly at `hausme-tech-interview-main`, and **27 files** if rooted directly at `hausme-tech-interview-pr` — because `.venv`/`.pytest_cache` are correctly gitignore-excluded and the embedded repo is invisible from the top-level root (see DF-H2). No genuine multi-thousand-file performance stress test was possible against this target as configured; the numbers below are real but small-scale.

## Step-by-step evidence

### 1. Pre-init status / context (unborn-HEAD root)

```
status  --mode code --root Husme  → {"ok":false,"error":{"code":"NOT_INITIALIZED","message":"OpenWiki is not initialized."}}   (118ms)
context --root Husme              → {"ok":false,"error":{"code":"GIT_FAILURE","message":"Unable to collect Git repository evidence."}}  (122ms)
```

`context` hard-fails on this root because `git rev-parse HEAD` fails on an unborn branch and `git.ts` `collectGitContext` collapses every git subprocess failure into the same `GIT_FAILURE` code (see DF-H1).

### 2. init → write 8 standard pages → check → finalize

`init --mode code --root Husme` succeeded (250ms), created `quickstart.md, architecture.md, source-map.md, workflows.md, domain-concepts.md, operations.md, integrations.md, testing.md` under `Husme/openwiki/`, computed `workspaceId 280b2367…`, and — notably — its own skeleton content was already self-consistent: `check` immediately after `init` (no writes) returns `{"ok":true,"issues":[]}` with no separate `finalize` needed. Good idempotency property.

I then wrote all 8 pages with real content synthesized from directory structure, dependency manifests, and graph output (grounded facts only — exercise names, tier names, file names, dependency package names; no quoted source or business calculations). `check` afterward correctly reported `STALE_STATE` (content differs from finalized state) until `finalize` succeeded — confirming the check/finalize consistency gate works.

`finalize` first attempt **failed** with a Python-generated (microsecond-precision) ISO-8601 timestamp: `INVALID_STATE: "Wiki state updatedAt must be a canonical ISO-8601 timestamp."` A retry with a JS `Date.toISOString()`-shaped (millisecond-precision) timestamp succeeded immediately. See DF-H3.

Post-finalize: `check` → `{"ok":true,"issues":[]}`; `status` → healthy, `contentHash` updated, `lastRun.command="init"`.

### 3. ingest (git-repo source envelope)

Built a schema-valid `SourceEnvelopeV1` (`schemaVersion:1, kind:"git-repo", provenance.host:"cli"`) from `hausme-tech-interview-main/README.md` (782 bytes, truncated to 4000-byte cap — well under it). `ingest --envelope-file` → `{"ok":true,"sourceId":"husme-main-readme","runHash":"9c4f40c2…","stored":true,"acceptedItems":1,"duplicateItems":0,"retainedRuns":1}` (114ms). Private data stored under `~/.openwiki/data/<workspaceId>/`, not inside Husme.

### 4. update (no-op path)

Per orchestrator override, no real commit was made in Husme. Tested the no-op detection two ways on the (untouched-until-then) `hausme-tech-interview-pr` root, which has a real commit:

- `context` **without** `--previous-head`: returns non-empty `changedPaths` (27 entries) — this is the "last 20 commits' file list" fallback, **not** "nothing changed since last update" (there is only one commit, so the fallback lists that commit's full file set).
- `context` **with** `--previous-head <current HEAD>`: returns `changedPaths: []`, `commitsSincePreviousHead: ""` — the true no-op signal, confirmed working correctly when used as designed.

This confirms the no-op mechanism itself works, but only when the caller supplies `--previous-head`; see DF-H4 for why this is a real footgun. On the literal Husme root (unborn HEAD), the no-op path cannot be exercised at all because `context` hard-errors (DF-H1) before reaching the "no changed evidence" check described in `openwiki-update/SKILL.md` step 3.

### 5. doctor

`doctor --mode code --root Husme` → all 9 checks pass: `node, permissions, git, manifests, config, state, locks, retention, secret-leakage` (136ms).

`maxFiles` safety ceiling is 50,000 (`graph-contracts.ts` `GRAPH_DEFAULTS`) — never approached here.

Ran the full read-action set against the `Husme` top-level build: `status` (141ms, `available:true, fresh:true`), `map --limit 50` (111ms, 31 modules, hubs across symbol/file/directory/module kinds, two duplicate single-node `cycles` entries for the same path — see DF-H5), `query --query quotation --limit 20` (99ms, 1 node match, confidence-graded diagnostics), `context --target <file> --limit 20` (111ms, 20 nodes/26 edges, confidence mix `resolved/exact/heuristic`), `impact --target <file> --direction both --depth 2 --limit 20` (110ms, 20 nodes/14 edges with traversal paths), `changes --limit 20` (122ms, `changeState:"working-tree"`, since an unborn-HEAD root can never report `clean`).

**Critical cross-check:** none of `build`, `map`, `query`, `context`, `impact`, or `changes` — across all 6 response bodies — contains the substring `hausme-tech-interview-pr` anywhere, including in the `diagnostics` arrays. The embedded repository's 27 real source files are completely invisible to the graph when rooted at the top-level `Husme` directory, with zero disclosed signal that anything was skipped. See DF-H2 (major).

### 7. MCP (JSON-RPC over stdio, `dist/mcp.js`)

`initialize` (client requested protocolVersion `2024-11-05`) → server responded `protocolVersion:"2025-11-25"`, `serverInfo:{name:"openwiki", version:"0.1.0"}`. `notifications/initialized` sent. `tools/list` → 13 tools, one per CLI operation (`init, status, context, search, read, write, ingest, finalize, check, doctor, schedule, purge, graph`), each with a well-formed JSON Schema `inputSchema` and MCP annotations (`readOnlyHint, destructiveHint, idempotentHint, openWorldHint`) — e.g. `status`/`context`/`graph` correctly marked `readOnlyHint:true`, `init` correctly marked `readOnlyHint:false`.

My first `tools/call` attempt used a wrong assumption (a single generic `"openwiki"` tool taking an `operation` argument) and correctly failed with `INVALID_ARGUMENT: "Unknown argument: operation."` — this was my scripting error, not a plugin defect; the design (one discoverable tool per operation, matching `openwiki-graph/SKILL.md`'s explicit warning to "use only the name returned by `tools/list`, never a guessed provider-specific name") is correct. Retried calling the `status` and `graph` tools by their real names directly: both returned results byte-identical in content to the equivalent CLI calls, wrapped correctly in MCP `content:[{type:"text", text:"<json>"}]` with `isError:false`.

### 8. Restoration

Husme was mutated in exactly two places, both fully accounted for and removed:
- `Husme/openwiki/` (created by top-level `init`/`write`/`finalize`) — removed.
- `Husme/hausme-tech-interview-pr/openwiki/` (created by a scoped `init` used only to test the no-op update path on a root with real commits) — removed.

No `AGENTS.md`/`CLAUDE.md` were ever created anywhere in Husme (the CLI runtime has no code path that writes them — confirmed by grepping `src/*.ts` for `AGENTS.md`/`CLAUDE.md`, zero matches; that instruction-block behavior described in the README is not implemented in this build). `hausme-tech-interview-main` was never touched (file mtimes predate this session throughout).

Post-restoration `git -C Husme status --porcelain` output is byte-identical to the pre-campaign baseline (`?? hausme-tech-interview-main/`, `?? hausme-tech-interview-pr/`, unborn `main`). `git -C Husme/hausme-tech-interview-pr status --porcelain` is empty (clean), HEAD unchanged at `3d78ab8d8e1704329e434b5c20d3593c2d5926b6`.

One environmental note: mid-session, `git status --porcelain` on the Husme root twice exceeded a 60–120s timeout under very high system load (`uptime` showed load averages of 14.5/11.7/9.5 against a machine running ~15 concurrent `gitnexus mcp` server processes and multiple other concurrent agent sessions); a plain `ls` on the same directory returned in 3ms at the same moment, and a subsequent retry of `git status` at lower load completed normally. This reads as environmental CPU contention, not a Husme integrity problem or a plugin defect — flagged for transparency, not filed as a DF.

## Positive findings (for balance)

- `init` produces an already-self-consistent baseline (no spurious `STALE_STATE` before any write).
- Subdirectory-scoped roots (not the git toplevel) work correctly and safely: `git ls-files` run from a subdirectory correctly scoped enumeration to that subtree with no `../`-path leakage or `PATH_OUTSIDE_ROOT` failures (confirmed empirically — the concern was raised as a hypothesis mid-investigation and empirically refuted).
- `doctor` cleanly passed all 9 checks throughout.
- `ingest` accepted a real, correctly-shaped `git-repo` source envelope end to end with correct dedup/retention accounting.
- MCP `tools/list` correctly exposes one discoverable tool per operation with accurate JSON Schemas and MCP annotations; MCP `tools/call` results for `status` and `graph` were byte-equivalent in content to their CLI counterparts.
- Bounded `--limit` and response-size truncation behaved exactly as documented across every graph read action tested.

- DF-H5 (duplicate self-loop cycle entries) and DF-H6 (56s vs. 1.1s vs. 667ms build-timing spread) were not fully root-caused within this session's timebox; both are flagged for Wave B with reproduction evidence, not closed findings.
